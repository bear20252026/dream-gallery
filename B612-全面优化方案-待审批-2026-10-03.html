一句话诊断

地基是好的，故事是半截的。前 7 场（坠机→画羊→B612→325→326→327）实现扎实、验收严格、台词逐字照搬原著，是可以拿出手的作品。但剧本定稿的 后 6 场（328/329/330 星球、沙漠现地五站、找井、告别、六年后的尾声）一行代码都没有，且有 57 条以上剧本原句在代码里找不到。

更关键的是：游戏目前是一串"可交互的对白"，还不是一本"可以翻的书"。「书页 x/9」只是个计数器，原著最核心的体验——一本画家飞行员的画册——在实现里没有对应物。

因此方案的骨架是：先补齐书（剧情 + 进度契约） → 再让书变成实体（签名机制） → 然后把地基修干净（性能与工程）。不是加更多特效。

问题 3 · 首屏被 26 次串行网络往返阻塞

世界模块用 for...of + await 串行加载，注释里写着「串行，阻塞揭幕」。26 个 chunk 逐个 RTT 往返。虽然每个包只有 17–24KB，但 26 次往返的累加延迟远大于并行。这是首屏最大瓶颈，而且很好修。

// world-loader.js:61-75 for (const load of loadChain) { await load(); } // 26 个独立 RTT

同时，11 处模型加载各自 new GLTFLoader().load()，无并发上限、无优先级、无全局进度。每个调用点独立 loader，LoadingManager 也各自独立，导致无法汇总加载进度——而项目目前也根本没有面向用户的进度条（onProgress 从未使用）。

问题 4 · 触屏笔记本会被误判成手机，砍掉 2/3 的灯

灯光预算用 ontouchstart in window 判移动端。触屏笔记本（含大量二合一本）会被识别为手机 → 只保留 1/3 吊顶灯 + 10% 射灯 + 512px 贴图上限。项目里其实已经有正确修法，只是没被采用：player.js:374 的 isFreshTouch()（800ms 内合成 mouse 事件才判触屏）。

light-sweep.js:10 const isMobile = 'ontouchstart' in window && Math.min(w,h) < 768; // ← 误判 light-budget.js:10 keepEvery: 移动3 / 桌面2 spotKeep: 移动4 / 桌面10 player.js:374 export function isFreshTouch() { ... } // ← 已有正解，未复用

顺带：loop-manager.js:128 的 lowQuality 提示写「PixelRatio=1」，实际最低档是 0.75，文案与行为不符。

问题 5 · 资源释放不成对（HMR 下会双跑主循环）

  • 全库 addEventListener 153 处 / removeEventListener 24 处；eventBus.on 9 处 / off 0 处。
  • 13 个 core 系统零 dispose，含主循环 loop.js——loop-manager.js:176 的 rAF 自续链没有停止点，_running 无外部置假路径。
  • postprocessing.js:12 的 composer 是模块级单例，持有一整套 RenderTarget 与 4 个 pass，无 dispose；星球世界切换时只把引用置 null，GPU 资源不释放。
  • openfilm.js:56 的 script:lang 监听在 done() 里漏清理——每次播开场电影泄漏一个 window 监听器。
  • 8 处模块级 setInterval 永不清理（mode.js / paintings.js×2 / quizgate.js / upload.js×2 / eternal.js / player.js）。

诚实的说明：单页应用只初始化一次时，"只增不消"是合理的，不会累积到致命。真正的风险在 hot.js 的热替换场景——重复执行模块顶层副作用会累积监听器和定时器。这与 system.js:22 声明的「dispose 支持热替换」契约相违背。

P1 2.5　尾声 · 六年后　闭环

八条台词（剧本 :1447–1517），是整个项目的收尾。

核心机制：第 1 场玩家画的是帽子还是蟒蛇，在这里被那个金发小孩问回来。玩家的选择穿越全书回到自己面前。这一步做完，整个游戏才从"一串场景"变成"一个故事"。

验收：读档时能取到开场选择；两种开场各有 2–3 项断言（可在纯逻辑层测，不依赖渲染）。

第 3 层　签名机制　—— 这一层是我的重点提案

前面两层是「把缺的补上」。这一层是回答一个问题：为什么这个游戏必须是 3D 的，而不是一本电子书？
答案是——原著里有些东西只有在三维空间里才成立：走远的距离、越来越小的星球、只能靠听寻找的井、五千朵一模一样的玫瑰、以及"驯养"所承诺的时间。

机制 A

书本身就是 UI：九页对开画册

"To Leon Werth, when he was a little boy." —— 献词背后，是一本画册

现在 J 键打开的「旅途手札」是一列 7 张卡片。把整个交互模型换掉：

  • J 键打开的不是任务列表，是一本你正在写的书。对开两页：左页原著英文（逐字，取自 Woods 译本），右页中文自译——双语同时可见，不再是切换按钮。
  • 每完成一段，右页留白处浮现玩家"看到"的那一笔。不是通用图标，是那一段专属的手绘插画（沿用现有 sketch() 铅笔线稿风格，每段一幅）。
  • 九页 = 九次开屏。翻书本身就是奖励，不需要额外成就系统。
  • 页脚留一个空白页——留给玩家自己写。可输入，存本地。这是最小成本的"私人化"。
为什么这个改动小、收益大：它不需要新系统，journeyNotebook 已经有渲染函数、存本地、跟随语言切换。改的是呈现，不是数据。相当于把一张清单换成一本书。
机制 B

五千朵玫瑰：一场不可能通过的挑战

"He thought he was rich, with a flower; but he was only poor, with a single flower." —— Ch.20

进入玫瑰园，用 InstancedMesh 铺 5000 朵（1 个 draw call，性能上完全可行）。然后：

  • 你那一朵没有任何视觉标记。没有高亮、没有光柱、没有唯一颜色。
  • 唯一线索是你此前在玫瑰站亲手记下的那一笔（香气 / 四根刺 / 藏起的眼泪）的抽象描述。
  • 玩家走遍全园按 E，每次"找到"的都不是他那一朵——因为"你以为是你的是哪一朵"本身就是原著的答案。
  • 刻意设计成无法被"刷任务"的心智完成。走完全园后由王子一句话收束，然后离开。
为什么值得做：这是全书唯一一处玩家必须接受"得到即失去"的关卡。别的关卡教机制，这一关教态度。放在书页八的末尾，从玫瑰园走回沙漠的十几步路上什么都不说，效果最好。
并且它完美利用了已有的 rose-gallery.js——建筑壳体已在，只差内容和那 5000 朵花。
机制 C

只能靠听的井：把罗盘反过来用

"You must listen. The well is singing." —— Ch.20

找井段落做三件事：

  • 主动关掉罗盘。它灰掉并显示"有些东西不是目标，是礼物"。这是对"游戏给你一切答案"的一次有意识的拒绝。
  • 用声音导航：屏幕边缘极淡的水波脉动，随距离衰减。不是箭头——是"听得见"的可视化。
  • 玩家必须真正静止 3 秒去听，脉动才会变清晰。风、虫、然后是很轻的水声。
  • 找到时：全黑，只有水声；然后水面反光铺开，倒映星。井边拾到的线索是第 12 场"画嘴套"的道具。
为什么值得做："重要的东西用眼睛是看不见的"在原著里是一句台词，在这里可以变成一个输入方式。这是 3D 和音频唯一不可替代的地方——纸书可以让你"想到安静"，但游戏能真的让你安静下来，而安静下来才听得见。
机制 D

驯养：让真实时间进入游戏

"Please — tame me. Let us be friends." —— Ch.21

狐狸要求「每天同一时刻来」。这是全书唯一一处让玩家的现实生活节奏成为机制：

  • 第一次在苹果树下按 E「约定」，玩家选一个时刻（游戏内显示，如"每天黄昏"）。
  • 此后每天那个真实时刻，苹果树下出现一个光点，狐狸在，来一次推进一天，共 4 天。存档跨会话持久化。
  • 第 4 天，狐狸说"我每天都在等"。如果玩家错过当天——狐狸仍在原地等。不扣分、不惩罚，但错过就是错过，次日可再来。
  • 诚实处理：允许玩家选「明天真的再来」或「缩短一天」。承诺过的等待权重更高，缩短的也仍然完整，但手札上会如实记录你选的是哪一种。
为什么值得做：这是唯一让玩家和"过去"建立非游戏内时间关系的地方。前四天之后，苹果树下那个光点会变成整个游戏里最重的一个像素。
风险要说清：真实时间机制只对愿意每天回来的人有意义，对一次性访客是空的。所以必须设计成跳过也能完整通关——四天可以压缩，甚至可以在同一会话内快进，只是手札上的措辞不同。
机制 E

星屑有了用途：手札 → 空画框

6 颗星屑现在只是任务册里的一个计数器（星屑 x / 6）。给它们终点：

  • 每颗星屑 = 手札里一页的边框插画。凑齐 6 颗，手札会变成一本完整的画册（与机制 A 同一个奖励出口）。
  • 回 B612 走完第 12 场"告别"后，玩家在永恒展厅挂出的画作旁，会出现一个空画框——第 13 场六年后的那个空框。
  • 尾声的"你画的是蟒蛇吗"由玩家在第 1 场的选择回答。这个选择存进 store，是全项目最长的一条因果链。
为什么值得做：把已有的三个系统（星屑计数 / 手札 / 展厅挂画）串成同一条线。这不需要新系统，只需要接线——但完成之后，项目第一次有了"从头到尾"的完整形状。
机制 F

原景回收：让"曾经路过"变成机制

把机制的注意力反过来：不只看"我要去哪"，也看"我是不是来过这里"。

  • 同一颗星球在回忆层和现实层各出现一次时，罗盘指针用两种颜色区分（"记忆中的位置" / "此刻的位置"）。
  • 第 10 场五站里，站三"山与回声"是唯一现实中存在过的地方——把之前彩蛋里播过的《登飞来峰》换掉，让山自己回应一次。这里是全项目唯一"改写既有内容"的地方，需要你拍板。

第 4 层　性能与工程

P2 4.1　首屏：26 串行 → 并行 + 真实进度条

把 world-loader.js 的 for...of await 改为受控并发（Promise.all 分批，或 p-limit）。注意：planets.js 必须在核心链（顶层副作用注册 worldManager），漏载会静默失败——石门消失。这是改造时唯一不能碰的红线。

同时把 11 处分散的模型加载收进一个统一调度器，接上 LoadingManager.onProgress，做真正面向用户的进度条。目前项目没有任何进度条，而 37MB 模型 + 26 个 chunk 值得一个。

验收：load-timing-probe.cjs 接入 npm test，首屏总耗时设上限防退化。改动前后各测 3 次取中位数。

P2 4.2　统一移动端判定（复用已有正解）

把 player.js:374 的 isFreshTouch() 提为共享工具，light-sweep.js:10 / scene.js:54 / light-budget.js / ark-freeflight-hud.js:56 / music-canvas.js:288 全部改用它。

顺带把断点体系统一：CSS 侧收敛为 600 / 960 两个（现在 600/640/768 三套并存，JS 与 CSS 还各用各的）。coord-hud.js 零响应式——固定 top:50% + min-width:138px，而它精心避让的任务卡和小地图在移动端都会移动，375px 宽下大概率重叠。补 @media。

验收：verify-hybrid.js 覆盖触屏笔记本；375 / 768 / 1440 三档截图无重叠。

P2 4.3　大模型分块 + 真正的 LOD

前 3 个 GLB 占 54%，且都是几何体大、贴图少。继续压缩收益已经见底（已全 meshopt+webp）。两条路：

  • 优先做 upper_vestibule.glb / picture_gallery.glb——它们不总是需要。用现有 35m 距离懒加载扩成 THREE.LOD：近处全几何，远处换低模或直接不画。
  • hall.glb 暂不动——它是建筑本体，几乎全程可见，分块收益低而风险高。
  • 把 7 处 frustumCulled = false 逐个审查，其中 sky-shader.js / fireplace.js 可能是必要的（超大或贴附地面），其余大概率是调试遗留。

验收：画质回归探针四检查点不劣化；perf-catwalk 移动场景 draw call 下降记录。

P2 4.4　让 dispose 契约真的成立

优先级从低往高排：

  • openfilm.js:56 的 script:lang 漏清理（每次播电影泄漏一个）——顺手修。
  • postprocessing.js composer 加 dispose，星球世界切换时释放。
  • 8 处模块级 setInterval 收进系统生命周期。
  • loop.js 给 rAF 自续链加停止点（这条是 HMR 双跑的直接成因，perf-monitor-system.js:4 的注释里记着这个历史踩坑）。

验收：新增 dispose-contract.test.js——每个 core 系统 dispose 后 renderer.info.memory 的 texture/geometry 计数不增长。这条测试会长期保护整个项目，比修 153 处监听器本身更值。

P2 4.5　自适应降级做完整

现在 adaptiveQuality() 只调像素比，不降后处理、不降灯数、不降 draw call。改成四档阶梯：

档 1（满） pixelRatio 2 + bloom + 全灯 档 2 pixelRatio 1.5 + bloom + 全灯 档 3 pixelRatio 1.25 + 无 bloom + 灯 ×0.6 档 4（保命）pixelRatio 0.75 + 无后处理 + 灯 ×0.35 + 阴影关

阈值（loop-manager.js:160/164 的 25 / 45）历史上收紧过两次却没有测试守护——把这段纯逻辑抽出来补单测，比调数字本身重要。

P3 4.6　测试与探针治理

  • 148 个探针里 144 个没进 package.json，靠手工 node。至少把 10 个关键验收探针（journey / story-chain / dialog-voice / scene-regression / 5 个剧情探针）接进 CI。
  • 补 3 类零覆盖区：adaptiveQuality 阈值逻辑、dispose 契约、8 个 @media 断点的视口重叠检测。
  • 设覆盖率下限（vitest.config.js 已装 v8 provider 但没 thresholds），先设一个不痛的数字卡住下滑。
  • 设 dispose 后 renderer.info.memory 回归断言（见 4.4）。

第 5 层　收尾与长期

P4 5.1　一句台词也不改的原则

补全 6 场时，英文逐字照搬 Woods 译本，与现有 story-text.mjs 的做法保持一致。中文自译。这个项目最值钱的资产就是"台词准确"，一旦掺进改写，信用就崩了。

新增内容（机制 B/C/D 的原创提示语）必须是玩家界面语言，绝不冒充角色对白——现有 journey-logic.mjs 已经有这个自觉（"小插画是手札里的铅笔图，不冒充剧情中的真实物件"），保持它。

P4 5.2　双语不是切换按钮

机制 A 落地后，对开页让双语同屏。body[data-script-lang] 的现有机制继续服务 UI 标签，但故事原文应该永远双语并列——这也顺带解决"英文玩家看不懂中文提示"的问题。

P4 5.3　不做什么（防止方案膨胀）

按"简洁优先"原则，明确划出边界：

  • 不改第 0–7 场的任何既有演出。它们是已经验收过的资产。
  • 不拆 planets.js（1092 行）——它因顶层副作用钉在关键路径，拆分风险远大于收益。只加注释说明为什么不能拆。
  • 不重写 admin.js（1605 行）——它和 3D 引擎无依赖，是后台单页，拆它对本项目零收益。
  • 不做 成就系统 / 排行榜 / 社交 / 联机。手札（第 3 层机制 A）已经是完整的情感出口，再加就是系统噪音。
  • 不压缩 hall.glb（7.59MB）——已全压缩，收益见底。
  • 不改已退役的灵蕴门槛分档方案、WEDDING_SHELL 落位偏移（用户 09-04 已拍板）、博物馆 mxY=30.1。
